- 后端按 provider 调整 LLM 并发：Ollama 本地 2 并发（CPU 推理高并发互相拖慢），DeepSeek 云端保持 12

### 问题与解决
- **LLM 模式一直「生成中」**：根因是 Ollama 0.32.14 的 llama-server 在 RTX 4060 Laptop 上 CUDA 初始化崩溃（0xc0000409 + "CUDA error: shared object initialization failed"，GitHub issue #17627 同款，未修复）。每次 LLM 请求 500 → 后端重试 → 全失败 → 降级要素池，期间前端一直 loading。
- **排查过程**：OLLAMA_NUM_GPU=0 无效（llama-server 二进制内嵌 CUDA 初始化）；cuda_v12/v13 后端均崩；清理 PATH 无效；更新 VC++ Runtime 14.51 无效（#17375 的方案针对的是不同错误码）；替换捆绑 DLL 无效；禁用 CUDA backend 目录无效（CUDA 内嵌于 llama-server.exe）。
- **最终方案**：`CUDA_VISIBLE_DEVICES=-1`（注意：空字符串会被 Ollama 环境传递机制丢弃，必须用 -1）强制 llama-server 跳过 CUDA backend，纯 CPU 推理。已验证稳定可用，且只影响 Ollama 进程树，不影响 PyTorch 等其他 GPU 程序。
- **速度实测**：Qwen3-8B Q5_K_M 纯 CPU 约 7 tok/s（16 线程），Vulkan backend 同为 7 tok/s（ggml Vulkan 实现尚不成熟）。生成 1 条约 20-30s（含模型加载），5 条一批约 5 分钟。大批量建议用 DeepSeek 云端。

### 关键认知（答疑记录，供后续调参）
- **max_rounds 本质 = LLM 重试预算（成本刹车），不是质量/速度旋钮**：正常一轮即满；轮数只在去重撞车/校验丢条时才消耗，耗尽是给 pool 让位（改造前）或如实报缺（改造后）。质量由 prompt/模型/校验决定；轮数越大 = 越多 API 调用 = 越慢越贵
- **缺口仅两个来源**：① LLM 调用失败——单次 0.5% × 2 内部重试 + provider 切换 + 8 轮续投 → 失败型缺量概率趋近 0（现状 39% 任务触发兜底恰因"单次失败即降级"过敏感，非 LLM 真不可用）；② 去重撞车——同类别并行 chunk 互不可见导致，串行化 + 全局窗口治理
- **物理边界**：LLM 服务整体宕机时「缺量 vs 混池」无第三态；按质量优先选缺量，走异常路径（报错 + 可续投），不在正常路径塞静默兜底
- 兜底日志路径确认：llm_client.py:454（失败降级）/468（成功计数），JSON 解析失败同样 return [] 走兜底（471），比原估更宽

### 阶段 3 收尾验证（同日续：缺口补齐演示通过 → 补齐流程加可见进度条）
- 端到端演示（浏览器手动，用户操作，3.6 缺口闭环）：制造缺口（临时禁用 provider → 生成全缺 → 橙色 ⚠ 状态条 + 「🔁 重试补齐缺口」按钮出现）→ 还原 .env/重启后端 → 点「补齐缺口」→ 补齐成功：预览数据追加至满量、meta 缺口归零、历史新增一条单次补齐记录 → **用户确认「补齐没有问题」** —— 阶段 3（窗口/轮数定档 + 跨文件去重 + 缺口展示与补齐）全部闭环
- 新需求（用户提出）：补齐缺口期间没有**可见进度条**——ProgressBar 仅在预览卡为空（首次生成加载态）时渲染，补缺时预览卡保持可见，状态条只有文本「⏳ 补齐中 n/m 条」。根因：fillGap 已逐文件新建 task 并轮询进度（数据在 progress.completed/_fillDone 里），只是没接到条形 UI 上
- 方案（纯前端，后端零改动）：预览卡内状态条下方渲染 ProgressBar —— completed = `_fillDone + progress.completed`（已完成文件条数和 + 当前文件轮询完成数），total = `_fillTotal`（全部文件缺额和），文件进度（第 k/n 个）仅多文件补缺时显示；状态条文本收敛为「⏳ 补齐中 · 第 k/n 个文件」，条数展示交给进度条避免双显；样式 `.result-meta + .progress-wrap` 左对齐随卡片宽
- 实现与验证（同日续，浏览器复演）：App.vue（状态条下渲染 `<ProgressBar v-if="fillingGap">` + fillBar computed）+ global.css 一行（`.result-meta + .progress-wrap` 随卡宽左对齐）；`npm run build` ✓ 796ms。浏览器复演：临时假 DEEPSEEK_API_KEY（备份 .env → sed → 重启后端，DeepSeek online:false）→ 2 类×20 条生成全缺 → 还原 .env 整文件（假 key 残留 0）+ 重启后端（online:true）→ 点「补齐缺口」→ **蓝色进度条随补齐每 1.5s 推进，补满后消失、状态条转绿 ✅，用户确认「非常顺利」** —— 补齐进度条闭环 ✓
